An AI agent is a software system that perceives its environment, makes decisions, and takes actions to achieve a goal. Unlike a simple chatbot that responds to a single input, an agent operates in a loop — acting, observing the result, and deciding what to do next. The loop continues until the goal is met or a stopping condition is reached.

Agentic AI systems are built around a core loop: the model receives a task, decides on an action, executes that action through a tool or API call, observes the result, and then decides the next step. This cycle repeats until the agent reaches a final answer or hits its maximum step limit. The ability to act across multiple steps is what separates an agent from a one-shot prompt.

Tools are the mechanism through which an agent interacts with the world. A tool is a function with a defined input schema and a predictable return value. Common tools include web search, code execution, database queries, and API calls. The agent does not execute the tool directly — it returns a structured call and the host application executes it and feeds the result back.

The orchestrator is the component that manages the agent loop. It sends the current conversation state to the model, receives the model's response, checks whether a tool was requested, executes the tool, appends the result to the conversation, and loops. Without an orchestrator, the model cannot act across multiple steps. In Claude's API, the orchestrator is code you write — it is not built into the model.

RAG stands for Retrieval-Augmented Generation. It is a pattern that gives an LLM access to external knowledge without modifying its weights. The idea is to retrieve the most relevant pieces of information from a knowledge store and inject them into the prompt before asking the model to generate a response. This grounds the model's answer in specific, verifiable sources.

The retrieval step in RAG works by converting both the query and the stored documents into vector embeddings. These embeddings live in a shared vector space where semantic similarity corresponds to geometric proximity. When a query arrives, its embedding is compared to all stored document embeddings using cosine similarity, and the closest matches are returned as the retrieved context.

Chunking is the process of splitting source documents into smaller pieces before storing them in a vector database. Chunks that are too small lose surrounding context — a chunk might say "he invented it" with no reference to who "he" is. Chunks that are too large dilute the embedding — the vector represents the average meaning of many sentences, making it harder to match a specific query.

A vector database stores document embeddings alongside their original text and optional metadata. At query time, you pass a query embedding and the database returns the k most similar documents by vector distance. ChromaDB is a commonly used open-source vector database that supports persistent storage, metadata filtering, and both in-memory and disk-backed collections.

The augmented prompt is the final prompt sent to the LLM in a RAG pipeline. It consists of the retrieved chunks injected as context, followed by the user's question. The system prompt instructs the model to answer only from the provided context and to explicitly say when the answer is not present. This prevents the model from hallucinating answers based on its training data.

Memory in agentic systems refers to how state is maintained across steps. Short-term memory is the conversation history — everything in the current context window. Long-term memory is typically stored externally, in a vector database or key-value store, and retrieved on demand using the same RAG pattern. Without explicit memory management, an agent forgets everything between runs.

Fine-tuning modifies a model's weights by training it on new examples. It is expensive, slow to update, and requires a full retraining cycle whenever the underlying data changes. RAG, by contrast, stores knowledge externally and retrieves it at inference time. Updating the knowledge base is instant — add or remove a document and the change is immediately reflected in responses. For frequently changing data, RAG is almost always the right choice.

Tool descriptions are critical to agent performance. When you define a tool, you provide a name, a description, and a JSON schema for its parameters. The model reads these descriptions to decide which tool to call and what arguments to pass. Vague or misleading descriptions cause the model to call the wrong tool or pass incorrect arguments. Writing clear, specific tool descriptions is one of the highest-leverage improvements you can make to an agentic system.

Safe execution means wrapping every tool call in error handling. A tool call can fail for many reasons: network timeout, invalid arguments, API rate limit, permission denied. If you do not catch these errors, a single failed tool call can crash the entire agent loop. The standard pattern is a safe_call wrapper that catches all exceptions, logs the error, and returns a structured error dict that the model can reason about and recover from.

Parallel tool calls occur when the model requests multiple tools in a single response. This is more efficient than sequential calls when the tools are independent. Claude's API returns multiple tool_use blocks in the response content when it wants to call several tools at once. The orchestrator must detect this, dispatch all calls concurrently, and inject all results back in a single user turn before the next model call.

The stop reason is how the model signals what it wants next. A stop reason of tool_use means the model wants to call a tool and is waiting for results. A stop reason of end_turn means the model has finished and is returning a final answer. The agent loop checks the stop reason on every model response to decide whether to keep looping or to return the answer to the user.
